## S28-V1 — suppress fade on a jump's completing frame too

The new `#labels.jump` rule disables transitions for galaxy/region/site labels and route legs. But `frame` chooses the class **after** `orbG.update`, or after `orbW.update` and `updatePlanet`. Those functions clear `.fly` / `.turn` when elapsed time reaches the duration (`engine.js:725,937`). Therefore, if a delayed frame covers the entire jump, the flags are already false and `labelJump(false)` runs before labels are laid out. The completing frame of a multi-frame jump similarly restores the fade before its layout. This leaves the large-jump edge case the change is intended to address.

[Source-order probe](supplementary-review-s28/delta-probe.cjs) executes the exact surface frame branch with fake update collaborators: motion active on entry and still active after update → jump true; motion active on entry but completed by update → jump false ([result](supplementary-review-s28/delta-result.json)). The galaxy branch has the same post-update ordering. This is a deterministic source-state finding, **not an independently observed new rendered failure**.

**Minimal correction:** preserve whether programmatic motion was active on frame entry and combine that with the post-update state, so fade remains disabled throughout the completing layout/paint; restore ordinary transitions only on a later quiescent frame. An equivalent bounded jump detector is acceptable. Acceptance: cover a full-duration first-frame delay, the last frame of an ordinary fly/turn, repeated jumps and subsequent ordinary motion in both galaxy and surface paths; verify stale labels/routes vanish without breaking normal fades. Keep the camera-matrix refresh ordering.
