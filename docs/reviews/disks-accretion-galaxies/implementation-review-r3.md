## Fallback and compatibility limits

Load, recovery and undo/redo supply a prior snapshot to `restoreUniverse`; their source call paths remain unchanged. The independent harness uses the actual restore, rebuild and capture-restore function bodies, the actual capture validators and accepted-body validator. It stubs body construction, camera, scene and UI work. It therefore tests fallback control flow and capture state, not full scene reconstruction or button interaction.

Three malformed snapshots (primitive, empty object, nonboolean original hold) return false and restore two prior bodies, donor mass 80, capture age 5, original hold false and active hold true; history suspension is cleared. A valid resumed snapshot with a false top-level hold instead returns true and becomes held. A null legacy capture retains its existing hold and restores no capture. The fallback test uses a valid prior snapshot: it does not promise recovery if the fallback is itself corrupt. Calls without a fallback do not gain transactional preservation from this patch; the reviewed Save/Load/undo/recovery paths supply one. Existing live capture cancellation uses the now-tested release helper.

The validator's “plain object” comment is broader than its actual prototype check: it rejects arrays and validates the boolean field but does not inspect prototypes. JSON-loaded objects are plain, so no additional blocker is asserted for unsupported class instances. Null's compatibility choice cannot recover capture information that no longer exists.
